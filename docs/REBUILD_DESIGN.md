## 1. 方針

1. **家族が根っこ**。データ・権限・請求・ログインを、家族 → 生徒 の向きで組む。
2. **役割で権限を決める**。
   - スタッフは1つのアカウントに役割（講師・教室管理者・システム管理者）を組み合わせて持つ。
   - サーバーは操作ごとに、必要な役割と見てよい範囲を確かめる。
3. **D1 を本来の形で使う**。
   - 表は名前の付いた列と ID で持ち、行ごとに書く。表を丸ごと書き直さない。
   - 「何列目」で書く処理をなくす。
   - Apps Script のコードを D1 の上で動かす今の仕組み（表計算のまね）は使わない。
4. **Apps Script は外とのつなぎだけ**。メールの送信とカレンダー・Meet の作成だけを頼む。今と同じ「控え（`_effects`）→ 頼む → 結果を書き戻す」形。
5. **スプレッドシートは写しだけ**。台帳の正本は D1。人が見るための写しと、バックアップに使う。
6. **画面は役割ごとに分けて、小さな部品で作る**。1つの大きなファイルに詰め込まない。
7. **今の仕組みは作っている間も動かす**。新しい仕組みは別の場所で作り、そろったら切り替える（6章）。

## 2. 全体の形

```
スタッフの画面 (/staff/)  保護者の画面 (/family/)  生徒の画面 (/student/?k=)
        │                    │                     │
        └──────────── Cloudflare Worker（新しい API）────┘
                         │            │
                        D1        控え（_effects）→ Apps Script（メール・カレンダー・Meet・Drive）
                         │
              毎日: 写し（スプレッドシート）・自動処理（請求の確定・仮予定の決定）
              毎週: バックアップ
```

- **画面**：
  - 今と同じく GitHub Pages（www.stepwise-education.jp）に置く。
  - 組み立ての道具（ビルド）は使わず、ブラウザがそのまま読める小さなファイル（ES モジュール）に分ける。公開の手順は今と同じ「push するだけ」のまま。
  - 予定表などの共通の部品は、3つの画面で同じものを使う。
- **API**：
  - 今の Worker の中に、新しい入口（例: `/v2/...`）として作る。
  - 処理は領域ごとのファイルに分ける（予定・記録・計画・請求・成績・給与・アカウント）。
  - 各処理は「ログインの確認 → 役割と範囲の確認 → 入力の確認 → D1 への書き込み（1つのまとまり）→ 控えに付随処理を積む」の順にそろえる。
- **同時に書いたときの扱い**：
  - 行ごとに版番号を持つ。
  - 画面が見ていた版と違えば「ほかの操作で変わりました」と返す。
  - 今の「台帳全体の版」はやめるので、カレンダーの書き戻しが消える心配もなくなる。
- **テスト**：
  - 今と同じ `node --test` と D1 の試験用の器（`test/helpers/d1-harness.cjs`）を使う。
  - 領域ごとにテストのファイルを持つ。

## 3. データの形

主な表だけを書く。すべての表に `createdAt`・`updatedAt`・`version`（版）を持たせる。お金に関わる変更は監査の記録（`auditLog`）にも残す。

### 3-1. 人とログイン

| 表 | 中身 |
|---|---|
| `families` | 家族（契約者）。表示名、メール、パスワード（PBKDF2）、状態（利用中・停止）、規約の同意、通知の設定 |
| `familySessions` | 保護者のログイン（端末ごと） |
| `students` | 生徒。`familyId`、姓名・ふりがな、学年・学校、専用リンクのコード、基本単価（計画の初期値）、授業の標準形式、在籍の状態（在籍・休会・退会）、生徒本人に許す操作 |
| `staff` | スタッフ。姓名、メール、パスワード（PBKDF2）、役割（講師・教室管理者・システム管理者の組み合わせ）、状態 |
| `staffSessions` | スタッフのログイン（端末ごと） |
| `staffRates` | 講師の時給の履歴（授業の時給・面談の時給・いつから）。源泉徴収の欄（甲欄・乙欄と扶養の人数）は `staff` に持つ |

- 1つの家族に生徒が何人いてもよい。生徒は必ず1つの家族に属する。
- 保護者のログインは家族に1つ（両親で共有）。
- 名前・メール・単価は、ここ1か所だけに持つ。今は名前が7か所、メールが4か所に写されている。

### 3-2. 予定

| 表 | 中身 |
|---|---|
| `lessons` | 授業。`studentId`、担当（`staffId`）、開始日時、分数、科目、種類、形式（対面・オンライン）、状態、締め切り、カレンダーの予定 ID、Meet の URL |
| `lessonRequests` | 生徒・保護者からの連絡。種類（日時の変更のお願い・お休み・開始を遅らせたい・キャンセル）、一言、受付時刻、誰から、処理の結果 |
| `cancellationFees` | キャンセル料の決定（規定額・減額・免除・理由）と、減額・免除の申請 |
| `sharedEvents` | 生徒・保護者が共有する予定（テスト・行事・授業ができない日） |
| `staffUnavailability` | 講師の休み（授業できない日時） |

| 状態 | 意味 |
|---|---|

- 初めての人は招待のメールから設定する。
- PIN はなくす。

## 6. 切り替えの進め方

### 案A（おすすめ）：横で作って、月初に一度で切り替える

- 新しい仕組みを別の入口で作る。画面は `/staff/`・`/family/`・`/student/`、API は `/v2/`。
- 作っている間、今の仕組みは不具合の修正だけにする。
- 全部そろったら、本番のデータの写しで移行を何度か試す。月初（請求の確定のあと）に、一度で切り替える。
- **一度で切り替えるのを勧める理由**：
  - データが少ない。生徒6人、授業68件、記録38件、計画17件。
  - 移行の手順を本番の写しで何度でも試せる。
  - 一方、少しずつ切り替えると、新旧の仕組みが同じデータを同時に書くための「つなぎ」が要る。家族が根っこの新しい形と、生徒が根っこの今の形の間では、そのつなぎが大きく複雑になる。
- **切り替えたあと**：
  - 今の画面は1か月ほど読むだけで残す。
  - 生徒の専用リンクのコードはそのまま引き継ぐ。
  - 保護者のパスワードも引き継げる。同じ方式なので、再登録は要らない見込み。

### 案B：領域ごとに少しずつ切り替える

- 例：成績や給与のような新しい領域から作って使い始め、最後に予定・請求を移す。
- 早く使い始められる。そのかわり、新旧のつなぎを作る手間と、二重に動く期間の複雑さが増える。

### 授業の予定の段階（2026-10-16）
本人の決定（2026-10-14、Kura `issues/stepwise-lesson-stages`）と規約 r9 第13〜15条に合わせて、授業の予定を **下書き → 調整中 → 確認待ち → 確定** の 4 段階にした（`0026_lesson_stages.sql`、`cf/v2/schedule.mjs`）。
- **下書き**（`held`）：塾だけ。作る画面の既定。
- **調整中**（`proposed`・`askedAt` 空）：保護者・生徒のページに出す。メールなし・締め切りなし・自動で確定しない。日時を直してもメールなし。`schedule/lessons/show`、作るときの `send: 'show'`。
- **確認待ち**（`proposed`・`askedAt` あり）：選んだ授業に締め切りを **1 つ** 付けて保護者にメール 1 通（`schedule/lessons/ask`、作るときの `send: 'ask'`、MCP の `notices/send`）。締め切りはお知らせから 3 日以上あと（翌月分だけなら今月25日）で、締め切りを置く授業すべての 2 日前まで。それより近い授業は締め切りを置かない（無回答では確定しない）。応答に LINE に貼る文（`lineText`。保護者ページの `#confirm` へのリンク）。日時を直すと調整中に戻る（締め切りを外す。メールなし）。
- **確定**（`decided`）：保護者ページの「この日程で大丈夫」（`family/lessons/agree`。画面で見ていた授業の id と版をそのまま送り、違えば何もしない。塾にメール）、締め切りの翌日 0:10 の自動確定（`autoConfirm`。何が確定したかを書いて生徒ごとに 1 通）、先生の確定（`schedule/lessons/decide`。合意の記録 `agreement` つき・メールなし）。日時を直すと保護者にお知らせ。
- 下書きに戻す（`schedule/lessons/unsend`）。保護者・生徒のページから消える。メールなし。
- 保護者ページ `#confirm`（日程の確認）：ログインしていなければログインのあとその画面へ戻す（`sw2_family_next`）。生徒のページからは押せない（合意は保護者）。
- 今日の「対応すること」に、調整中のまま 5 日以内に来る授業。
- 今の行の読み替え：締め切りのある `proposed` は確認待ち、締め切りのないものは調整中。

### 5段目：授業計画・キャンセル料・請求（2026-10-02）

- **表**（`cf/migrations-v2/0006_billing.sql`）

### ファイルの置き場所（2026-10-02）

成績票・請求書・領収書・講師の給与明細・契約書など、**すべてのファイルを1か所で持つ**。領域ごとに置き場所を作らない（あちこちに散らばらないように）。

- **どこに**：Cloudflare R2（バケット `stepwise-files`、公開しない。binding `FILES`）。Google Drive と比べて決めた。
  - 保護者・生徒は Google のアカウントを持っていないことが多い。R2 なら、ほかの画面と同じログインで、だれが開けるかを1か所で決められる。Drive だと「リンクを知っている人」の共有（漏れるおそれ）か、Apps Script を通す（遅い・大きさの限り）しかない。
  - 無料の範囲（10GB、取り出しは無料）で何年分も足りる。
  - 代表が Drive で見られる便利さは、月に1回 Drive に写しを置く形で補う（まだ作っていない）。
- **台帳**（`cf/migrations-v2/0010_files.sql`、`cf/v2/files.mjs`）：`files` 表に、種類（scoreSheet・invoice・receipt・payStatement・contract・other）、持ち主（家族・生徒・スタッフ）、つながる先（`refType`・`refId`。例: 試験・請求・報酬の月）、名前・種類・大きさ・SHA-256・送った人を持つ。
  - R2 の鍵は `f/<id>` だけ。名前や家族は入れない。生徒が家族を移っても名前を変えなくてよい。「フォルダ」は持たず、一覧は表から作る。
  - 領域の状態（例: 成績票の取り込み待ち）は領域の表（`examFiles`）に持つ。
- **だれが開けるか**（`canRead` だけで決める）：教室管理者はすべて。講師は自分の給与明細だけ。保護者は自分の家族（生徒の今の家族を含む）の成績票・請求書・領収書・契約書。生徒は自分が送った成績票だけ。
- **送る**：領域の操作（例: `family/grades/upload`）が行を作り、送る鍵（10分・1回）を返す → 画面が `POST /v2/files/put?t=鍵` に中身をそのまま送る（20MB まで）。サーバーは大きさと中身の先頭（PDF・JPEG・PNG・WebP）を確かめてから置く。種類を付けずに送るので、ブラウザの事前確認は起きない。
- **開く**：`files/link` で開く鍵（5分。PDF の表示のため期限内は何度でも）→ `GET /v2/files/get?t=鍵` を新しいタブで開く。`no-store`・`nosniff`。
- **お金の書類**（請求書・領収書・給与明細）は7年消せない（`retainUntil`。電子帳簿保存法。日付・金額・相手で探せるように、台帳と請求の表に持つ。細かいところは税理士に確認する）。システムが作る書類（請求書の PDF など）は `putGenerated` で置き、発行したあとは変えない（出し直すときは新しい版を作る）。
- **片づけ**：送られなかった行（1日たった pending）と切れた鍵は、毎日0時10分に消す。
- **テスト**：`test/v2-files.test.cjs`（テストでは R2 の代わりにメモリを使う。`test/helpers/v2-harness.cjs`）。
