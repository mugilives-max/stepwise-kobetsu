### 入口と操作の順番

代表は設定の「雇用・勤務」から講師を下書き登録する。スタッフ一覧にも雇用登録へのリンクを置く。講師は設定から自分の雇用・勤務を確認する。契約準備中の新規アカウントは、この画面を最初に開く。

| 手順 | 操作・確認 |
|---|---|
| 1. 下書き登録 | 氏名を登録し、本人のメールアドレスは下書きでは任意。保存だけでは送信しない。住所、契約期間、勤務可能時間、他の勤務先、申告書・振込同意等を確認して保存 |
| 2. 契約書案 | 紙・電子を選び、保存済みの条件から本文を固定。全文を開いてPDF保存。代表がその版の内容を確認・合意して発行 |
| 3. 締結・交付 | 下記の紙／電子の経路に従う。アカウント設定・PDF生成・書面の交付・本人の合意を別々に記録 |
| 4. 給与・招待 | 契約の時給と確認済み申告書区分を給与設定へ反映。本人のメールアドレスを保存・宛先確認後に招待し、本人がパスワードを設定 |
| 5. 初日の勤務 | 授業・見学・準備・休憩を含む勤務予定を代表が登録し、本人が確認。契約・給与・書類・予定の確認がそろってから、代表が業務画面を有効化 |
| 6. 実績 | 本人または代表がその日全体の実績を登録。代表が実績と賃金調整を確認。訂正前の時間と理由も履歴に残す |
| 7. 給与 | 確認済み実績を既存の月次給与へ反映。本人は自分の明細を閲覧・PDF保存。振込は別途行い、実際の支払い後に記録 |

新規の雇用準備用アカウントは、準備を確認するまで生徒情報へアクセスできない。準備未確認・契約期間外の将来の担当割当も止める。既存アカウントの利用権は移行時に変更しない。過去に働いた事実は、契約未完了・期間外でも勤務実績に残せる。

### メール未定の下書き（2026-10-17採用、公開準備中）

本人の指示により、下書きではメールを任意、招待時は必須とする。空欄をそのまま保存し、仮のアドレスを生成しない。複数人をメール未定で保存できる。入力した場合は形式と既存スタッフとの重複を確認する。

代表は「給与・アカウントの準備」で、招待前のメールを後から保存できる。保存だけではメール送信・契約発行・アカウント有効化を行わない。未登録なら招待操作は出さず、APIも招待を拒否する。送信前に表示した宛先への明示確認が必要。招待済みの宛先変更はこの機能に含めず、既存の契約固定版・同意・給与を変更しない。

移行0029は、スタッフのメール一意索引を空欄以外に限定する変更のみ。既存行を削除・更新しない。旧コードへ戻す場合も索引を無条件に旧仕様へ戻さず、メール未定の下書きを残す。

### 紙・電子の締結

**紙**：代表が固定版を発行 → 印刷・署名・双方への控えの交付 → 代表が実際の交付日時、署名日時、講師氏名、署名済み控えの非公開保管先を記録。実際の署名時刻と記録時刻を分け、転記を本人の電子同意とは表示しない。

**電子**：代表が固定版を発行 → 本人がアカウント設定 → 電子交付の希望と受取先を指定 → 代表がPDFを実際に送付して交付を記録 → 本人が「同じ版を受領し、保存・印刷できること」と「本文への同意」を確認し氏名を入力 → 双方が締結・交付記録付きの控えを保存。

PDF送付は代表が本人指定先へ別途行う方式。PDF添付メールの自動送信は今回追加していない。ページへの表示を交付済みにはせず、電子交付の希望と契約内容への同意も区別する。[厚生労働省FAQ](https://www.mhlw.go.jp/bunya/roudoukijun/faq_kijyunhou_4.html)。

発行後にプロフィールを直しても発行済み本文は変わらない。変更時は新しい版を作り、前の契約・同意・交付履歴を保持する。重複する未締結版は先に取り下げる。締結済み版は削除・取り下げしない。[雇用契約書ひな形](EMPLOYMENT_CONTRACT_DRAFT.md)は締結方法の説明のみ整合し、[変更前](archive/employment-contract-before-dual-route-20261017.md)を保存。時給等の条件と3章の未採用案は変更していない。

### 勤務と給与

- 開始・終了・仕事の種類・内容を入力。区分は授業、準備・記録、事務・見学・研修、面談、休憩。重複する時間は登録できない。授業予定から、重複を除いた準備・記録の前後5分を勤務案として表示する。
- 勤務予定の変更時は本人の確認を取り直す。実績には既に働いた時間を記録する。実際の準備・記録が初期値より長い場合も入力できる。
- 実績を提出した日は、**その日全体の実績**で給与を計算し、授業・面談からの自動計算を重ねない。実績未登録の日は従前の自動計算を維持。代表未確認の実績は給与確定を止める。
- 架空例：準備5分、見学45分、途中から授業45分、記録5分＝100分。時給2,000円で3,333円。同日の授業90分や自動準備10分をさらに足さない。生徒側の授業・回数・請求・同意は変更しない。
- 確定済み給与は固定。本人の訂正申出を代表の一覧・講師詳細に表示し、対応結果も保存。給与訂正が必要なら既存の取消・再確定を先に行う。申出や回答だけでは金額を変えない。
- 休憩不足・深夜・長時間勤務・契約期間外・兼業等は要確認を表示。割増賃金・休業手当は自動算定せず、代表が実態を確認し給与調整へ根拠を残す。保護者の取消料から自動決定しない。
- 面談給は未設定を表せる。任せる前に書面と設定を整える。支払日は翌月25日、銀行休業日なら前営業日。2026・2027年の祝日を確認済み。未収録年の給与確定は止める。

## 保護者通知と導線の改善手順案（2026-10-16）

### 0. 着手時に固定する範囲

1. 最新の main、公開中の画面・Worker・メール代行の版を照合し、調査後に他の作業が入っていれば対象の差分を読む。GitHub上の作業を継続する。

4. 改修後の主要な流れを先に決める：通知 → 必要ならログイン → 対象の確認 → 承認／連絡／振込 → 完了表示・控え。この順に欠ける情報を埋める。

### 1. 送信結果と日程確認の不整合を直す

**1-A：送信結果を通知ごとに確かめられるようにする。**

- Workerとメール代行の間で、送る通知と処理結果を同じ識別子で照合する。HTTP全体の成功とメール1件の成功を分ける。複数件の一部失敗や代行の処理上限も扱う。
- 「送信できた」「送信できなかった」「結果が確認できない」を区別する。宛先未登録・登録未完了・テスト用で送らない場合も、教室が理由を分かるようにする。「送信できた」は受信箱への到達や既読を意味しない。
- 送信成功後に応答だけ失われる可能性があるため、結果不明を単純に失敗として一括再送しない。通知IDと代行側の処理記録で照合できる範囲を決め、照合できないものは管理者の確認対象とする。メールの完全な1回送信を保証できると説明しない。
- 再送は対象と最新の有効性を確認する。取消済み・変更済みの日程、古い請求、期限切れの登録リンクを、そのまま新しい依頼として送り直さない。新しい内容で再案内する場合は、元の通知を残して別の通知として記録する。
- 過去の sent を一律に失敗へ書き換えたり、一括再送したりしない。必要な過去調査は対象を限定して行う。
- 通知未達時の自動確定は下の判断D1として扱う。結果判定の修正だけでこの運用課題が解決したことにはしない。

**完了条件**：個別失敗・一部成功・HTTP失敗・応答不明・再試行・同時処理で、表示が実際の確認結果に合う。メール以外のカレンダー連携も維持する。対応する失敗が管理者の確認一覧に出る。

**1-B：日程確認で「表示したもの」と「確定するもの」を一致させる。**

- 子どもの選択を先に確定してから一覧を作る。メールに対象生徒が指定されている場合は、その家庭内の生徒を選ぶ。旧リンクなど指定がない場合は、家庭全体の確認待ちを生徒別に示す案を推奨する。
- 生徒別・回答期限別にまとめ、返事をもらってから決める直近の授業は別に表示する。最も早い期限を一覧全体の期限として示さない。
- ボタンには「表示中の○件」など対象が分かる文を置く。表示した授業ID・版を送るまで固定し、子ども切替や再描画で別の集合へ黙って変わらないようにする。
- 開始済みの授業、変更の連絡への回答待ちは、一括確定できる対象から除き、除外理由を示す。途中で内容が変わった場合は再確認を求める。
- 全件の事前確認と更新の間に他の操作が入る場合も確認する。更新する各行の版を照合し、一部だけ確定して「全件完了」と出さない。可能なら全件を一度に確定し、できない設計なら結果を件数・対象つきで明示する。

**完了条件**：子ども未選択・別の子ども選択済み・兄弟各1件・複数期限・期限なし・開始済み・連絡中・別操作での変更で、表示件数と操作結果が一致する。今までの合意・記録を消さない。

主な対象：`cf/v2/effects.mjs`、`effects-admin.mjs`、`gas-effects/Code.gs`、`family/app.js`、`cf/v2/schedule.mjs`。

### 2. メールから対象へつなぎ、戻れるようにする

1. まず通知の分類と移動先を共通化する。合意書・条件書・請求・料金回答は「お支払い」、日時の確定・変更は「予定」、日時への返事は「日程の確認」へ進める。ホームに戻るだけの通知を減らす。
2. その上で、対象生徒・月・書類／授業の識別子・必要な版を引き継ぎ、該当カードや詳細を開く。メールを作る箇所ごとに別々のURL規則を作らない。IDは場所を指定するためのものであり、ログインや家族の閲覧権限の代わりにはしない。
3. 受講合意書は「その月の全件」と「今回通知した対象」を区別する。リンクを開くまでに追加された別の合意書を、同じ依頼として黙って承認させない。古い版は控えとして見られ、新しい案があると分かるようにする。
4. すでに承認済み・確定済み・取消済み・内容変更済みなら、現在の状態と次の確認先を表示する。「ありません」だけで終わらせない。旧メールに対象情報がない場合は、特定の通知の結果を推測せず「現在の一覧」を示す。
5. 通常ログイン後の復帰を対象IDまで引き継ぐ。再設定メールを別タブで開いた場合も、元の用事へ戻れる手段を作る。戻り先は許可した保護者ページ内に限定し、任意の外部URLへ飛ばさない。登録・再設定の鍵を通常の業務リンクや記録に流用しない。
6. 日程については、既存の「家庭の現在の確認待ち一覧」を改善する案を先に進める。過去の依頼そのものを再表示する専用ページは判断D4で分離する。

**完了条件**：ログイン済み／未ログイン／別タブで再設定／処理済み／内容変更済み／他の家庭のID／旧形式のURLで確認する。他の家庭の内容を出さず、対象を勝手に別のものへ置き換えない。通常のメニュー操作と古いリンクも使える。

主な対象：通知を作る `schedule.mjs`・`billing.mjs`・`conditions.mjs`・`specials.mjs`、`family/app.js`、必要に応じて `accounts.mjs` と家族向け読み取りAPI。

### 3. 文面・支払い・困ったときの案内をそろえる

**3-A：現行13種類の通知について、本文と画面を一組で見直す。**

文面作成時の対応表は [メール通知の改善設計](EMAIL_NOTIFICATIONS.md#parent-notification-copy-plan-20261016) に置く。各メールは「対象 → してほしいこと／お知らせだけ → 期限・返事がない場合 → 対象を開くリンク → 困った場合の連絡先」の順を基本とする。既定の期限がないものに新しい期限は足さない。

- 件名は用事と対象月を先に示す。生徒名は本文で示す案を基本とし、件名に個人情報を増やさない。
- 合意書は科目・回数・時間・料金、日程確認は日時、請求は確定した支払い額、と目的を分ける。予定総額と請求額を同じように見せない。
- 承認できないときは、必要な規約・条件への同意と、先に行う操作をボタン近くに示す。変更希望・相談の入口も置く。
- 承認完了後は結果と「控えを見る／印刷・PDF保存」へ案内する。確認操作をもう一度求めるような完了文にしない。
- 連絡先は、既定のLINEとメールアドレスを用いる。メールにそのまま返信できるかは送信元・返信先を実際に確かめてから書く。
- 増やすメールの種類は判断D2で決める。今回の文面整理だけで全操作に完了メールを付けない。

**3-B：支払いに必要な情報を手前に出す。**

- メールは対象月・合計・支払期限・請求詳細へのリンク、画面は内訳・支払期限・振込先の確認・振込後の連絡、の順に整える。口座情報はログイン後の画面／請求書で確認する案を基本とする。
- メール・画面・請求書で同じ期日を参照する。休日を含む実際の期日の表示方法をそろえる。遅れて確定した請求は判断D3を解決してから適用する。
- 既に発行した請求書や合意済みの支払条件を、今回の表示整理で書き換えない。訂正が必要なものは元の内容と理由を残す既存の手順へ分ける。

**3-C：登録・再設定に失敗しても次の行動を示す。**

- 登録済みならログイン、招待が無効なら教室に再案内を依頼、再設定が無効なら再設定のやり直し、の入口を作る。

- 元の用事が分かる場合は「日程を確認するためにログイン」などと示す。ログイン前に生徒名や料金は表示しない。

**完了条件**：13種類それぞれについて、件名・本文・到着画面・ボタン・完了表示を並べて確認する。日時確認と料金承認、予定額と請求額、回答期限と支払期限を取り違える説明がない。

3. 確認用の受信先に限定し、架空の内容で実メールから操作する。実在家庭にはテスト通知を送らない。受信先・差出人名・返信先、PCとスマートフォンでのリンク・ログイン・完了・PDF保存を確認する。
4. 既存の契約・同意・請求・書面が保持されたことと、新しいエラーの有無を確認する。公開時の送信停止・再開は、既存の pending を一括再送する操作にしない。
5. 結果をGitHubの該当文書とKuraへ記録する。実装済み・公開済み・実受信確認済みを分けて書く。

### 初回の完成範囲と後回しにするもの

初回は「現在送っているメールから、正しい対象を確認し、完了できる」ことまで。送信結果の判定、日程確認の正確さ、対象への移動、文章、復旧、支払い案内をひとつの利用の流れとして確認する。

日程依頼ごとの新しい専用ページ、全通知を集約する新画面、通知の好みの細かな設定、全操作の完了メール、規約の再改稿・名称変更は初回の必須条件にしない。必要性が確認できたものを別に進める。

### PN-01：通知のリンク先を用事に合わせる

### PN-02：日程確認の対象と期限を一致させる

`#confirm` はメールで送った授業だけではなく、現在の家庭の確認待ち一覧を表示する設計。さらに、このタブで以前選んだ子どもを覚えているため、二人目の通知を開いて一人目が選ばれたままだと「いま確認をお願いしている授業はありません」と出る。

初回の子ども未選択時には、一覧を作ったあとに子ども選択が一人目へ変わる。架空の兄弟各1件では、**画面に2件の授業と「2件を確定」が出るのに、クリック時の対象は一人目の1件**となった。ただし後続の確認ダイアログには再計算した件数が出るため、黙って2件分を誤って確定した、とまでは言えない。

また、別々に送った依頼の期限が混在すると、説明の冒頭は最も早い期限一つで「この日時で確定します」とする。各授業の詳細には個別期限があるが、一覧全体の説明が一致しない。今日すでに始まった授業も日付だけの絞込みでは残り、サーバーで「始まっている授業が入っています」と拒否される可能性がある。

**案**：表示前に子どもの選択を確定し、表示したID・版の集合をボタンまで固定する。リンクが指す生徒を選ぶか、家庭全体を明示した一覧にする。期限別・「返事が必要」の群に分ける。現在の集合一覧を維持できる改善を先に行い、依頼ごとのページを新設するかは別に判断する。

根拠：[子どもの選択](https://github.com/mugilives-max/stepwise-kobetsu/blob/d13c5e0ce8b7f34a41b8a8e446d4aab096e36a36/family/app.js#L72-L84)、[日程確認の描画](https://github.com/mugilives-max/stepwise-kobetsu/blob/d13c5e0ce8b7f34a41b8a8e446d4aab096e36a36/family/app.js#L162-L175)、[クリック時の対象](https://github.com/mugilives-max/stepwise-kobetsu/blob/d13c5e0ce8b7f34a41b8a8e446d4aab096e36a36/family/app.js#L335-L339)、[サーバーの拒否条件](https://github.com/mugilives-max/stepwise-kobetsu/blob/d13c5e0ce8b7f34a41b8a8e446d4aab096e36a36/cf/v2/schedule.mjs#L358-L380)。

### PN-03：送れなかった通知を成功扱いしない

送信代行はメール単位の例外を `failed` に入れ、全体として `ok:true` を返す。Worker側はHTTPや全体エラー、カレンダー作成の失敗を判定するが、`failed` 内のメール失敗を参照しない。架空の「送信上限」エラーを返すと、実際には0件の成功なのに `sent:1, failed:0` と記録された。

この状態は管理者の失敗一覧・自動再試行にも出ない。さらに、日程の自動確定は授業の期限等を見ており、通知の送信成功とは結び付いていない。これは運用上の確認課題であり、本番で実際に未着があった、または契約上の効果がどうなる、と結論づける調査ではない。

**案**：代行の結果を通知ごとのIDで照合し、「成功・失敗・結果不明」を分ける。結果不明を再送する際の重複対策も決める。送れなかった日程依頼をLINE等で案内し直す場合、実際の通知時刻と回答期限の確認を管理者に促す。過去の sent を一括再送する対応は避け、必要なら個別に調査する。

根拠：[代行の結果](https://github.com/mugilives-max/stepwise-kobetsu/blob/d13c5e0ce8b7f34a41b8a8e446d4aab096e36a36/gas-effects/Code.gs#L29-L42)、[結果判定](https://github.com/mugilives-max/stepwise-kobetsu/blob/d13c5e0ce8b7f34a41b8a8e446d4aab096e36a36/cf/v2/effects.mjs#L18-L39)、[再試行対象](https://github.com/mugilives-max/stepwise-kobetsu/blob/d13c5e0ce8b7f34a41b8a8e446d4aab096e36a36/cf/v2/effects-admin.mjs#L60-L67)、[自動確定](https://github.com/mugilives-max/stepwise-kobetsu/blob/d13c5e0ce8b7f34a41b8a8e446d4aab096e36a36/cf/v2/schedule.mjs#L185-L200)。

### PN-04：何の合意・確認なのかを一文で伝える

受講合意書は科目・回数・時間・料金、日程確認は授業日時を扱う。今のメールも別件名だが、初回合意書メールには時間・単価がなく、再案内には単価があるなど、説明粒度が違う。「受講合意書」だけで用事が伝わるかは確認したい。

「お支払い」には規約、条件書、合意書、請求が集まる。規約・通常条件への同意待ちだと合意書の承認ボタンが無効になるが、そのボタンの直前に「先に何をすればよいか」の理由表示がない。表示順はすでに規約→条件→合意書なので、構成の作り直しより短い説明が先。

**案**：「11月の授業内容・回数・料金をご確認ください（受講合意書）」のように用事を先に書く。「この操作は授業日時の確認です。科目・回数・料金の承認とは別です」を日程確認の入口に短く添える。無回答で合意書への承認が成立すると受け取れる文は使わない。変更希望時の連絡先、承認後の控え・PDF保存への案内もそろえる。

招待の「授業計画」、システムの「受講条件書（通常指導）／特殊指導」と規約r9の名称差は既知の残件。名称だけ先行変更せず、実際に適用する版と画面・書面をそろえる。

### PN-05：ログイン・登録エラーで迷わせない

### PN-07：古い通知・回答後にも状態を理解できるようにする

日程確認は現在の未処理一覧なので、古いメールを開いても当時の依頼だけが開くわけではない。処理済みなら「確認をお願いしている授業はありません」となるが、確定済みなのか取り下げられたのかは分からない。期限が異なる新たな依頼も混ざり得る。

日時変更メールに生徒名・科目がなく、免除申請への回答には対象日時がない。兄弟や複数申請があると特定しづらい。請求を取り消したときは v2 の保護者通知がなく、古い請求メールを見て行動する場合に取り消したことが伝わりにくい。

**案**：用事を特定する最小情報を入れ、解決済みのリンクには「対応済み／変更あり」と現在の控えを示す。変更・取消しメールには返事が必要か、料金がある場合は即時支払いなのか次回請求に含むのかを明示する。規約の案内・請求取消しなど重要な変更を別途知らせる範囲と、操作完了メールを増やすかは分けて判断する。

## 授業記録の目的と要件（2026-09-22の対話）

### 合意した目的と優先順位

1. **保護者への報告が第一**。個別指導の授業内容が保護者から見えにくくなることを防ぎ、「こんな授業をした」と伝える。先生の詳細な評価入力そのものを目的にしない。
2. **送信した授業計画との対応**。どの計画の何回目で、どういう位置付けの授業かを分かるようにする。先生のペース配分と、保護者が授業の必要性・追加が必要な理由を理解することにつなげる。
3. **次回までの宿題の登録・管理**。ノートのメモだけでは管理しづらい生徒を支援する。複数科目や課題量の増加により、残りの課題やペースを把握しづらくなることも課題として扱う。

先生が以前使っていた紙の記録には、理解度、宿題の実施・忘れ、正答率、テストまでの授業回数などがあった。しかし、PC・スマホで毎回細かく入力する負担が大きいため、すでに簡素化を進めてきた。項目が多いと視線が散り、どこに入力すべきか分かりにくいという本人の問題意識を、今回の設計の出発点とする。

### 合意した基本方針

- **主要な入力は「扱った範囲」と「コメント」の2つ**。範囲には単元だけでなく教材・ページ・問題番号も書ける方向とする。理解できたこと、つまずき、次回の対応は短いコメントで伝えられ、毎回別欄へ分けて入力することは前提にしない。
- **必要な情報と手入力する項目を区別する**。日時・科目・対象の計画・回数・次回予定など、既存データから分かるものは再入力させない。対象計画など未接続の情報は、正しい関連付けを設計してから表示する。
- **毎回書くものが自然に目に入る**。宿題・持ち物・連絡は必要に応じて使う。前回情報・準備・先生専用メモ・詳細評価が、保護者向け報告の主要入力と同じ強さで並び続けないようにする。
- **詳細項目を一律に廃止する決定ではない**。理解度・進度・正答率などの既存値は保持し、集計や講師間の引き継ぎに独立した項目が必要かを別途判断する。表示の整理とデータ削除を同一視しない。
- **同じ内容を二重入力しない**。報告と宿題管理には入力済みの情報を再利用する。今回の初回実装では確認後の公開・反映を一連化し、既存の別処理・再送・競合・完了状態の保護を維持する。
- **PC・スマホの両方で日常的に入力できること**を条件とする。文章を短く書ける設計にするが、固定の行数で本文を切り捨てたり、長文を必須にしたりしない。

### 情報の役割と扱い方

以下は基本方針に沿った情報整理。配置・折り畳みの試作は後述。今回採用した必須入力や保存・公開条件は仕様の正本に記載する。

| 情報 | 役割 | 扱い方の方向性 |
|---|---|---|
| 扱った範囲・コメント | 保護者が授業の内容と様子を理解する | 入力の主役。必要な説明を短くまとめる |
| 生徒・日時・科目 | 対象の授業を明確にする | 既存の予定・記録から自動表示 |
| 対象計画・内訳・何回目・残り・次回予定 | 全体の中での授業の位置を理解する | 計画全体の回数と内訳内の回数を区別。正しい関連付けから自動表示する方向 |
| 宿題・持ち物・連絡 | 次回までの行動を明確にする | 必要なときに入力。通常の期限は次回の同じ科目の授業を使う方向 |
| 前回の記録・宿題・準備 | 今回の指導を判断する | 参照情報として使い、転記させない |
| 先生用メモ・詳細評価 | 先生の補助、必要時の評価・引き継ぎ | 主入力を妨げない扱いを検討。非公開情報は分離 |

### 計画との対応で注意すること

- **回数上の位置と、学習上の位置付けは別**。「全何回のうち何回目か」は集計できても、「何のための授業か」「なぜ追加が必要か」は回数だけでは説明できない。計画の目的と今回の範囲・コメントを合わせて伝える方向で検討する。
- 初回調査の [lessonWorkspace_](../gas/LessonCycle.gs) は、同月・同科目の確定予定から順番を計算する。これは送信した計画への所属を表すものではなく、そのまま「この計画の何回目」と表示しない。
- [管理画面](../kanri/index.html) の `renderPlanUsage` は、期間・種類・追加案内を扱う計画の消化状況を別に表示している。既存の計画・割り当て処理と整合させる必要がある。
- 月をまたぐ計画、同科目の異なる種類、追加授業、送信済み・承認済みの区別、変更後の過去記録の扱いは未決事項。不明な対応を推測で確定しない。
- 追加が必要かは学習上の課題を踏まえた先生の判断と理由で伝える。残り回数だけで自動判定したり、料金承認・請求のルールを変更したりしない。

### 宿題管理で注意すること

- 先生側は宿題内容を一度入力し、報告と生徒の課題に再利用できることを目指す。期限の既定値と例外の変更は分かるようにする。
- 生徒側では、科目をまたいで「何が残っているか」「いつまでか」が分かることが重要。宿題を登録する画面と、生徒が実行を管理する画面は分けて設計する。
- 大きな課題の小分けや途中期限によるペース配分支援は**候補**であり、まだ実装範囲に含めない。先生が毎回細かい計画を入力する負担を増やさないことを条件に、別途必要性を確認する。

### 授業計画の内訳：任意の高度な設定

**合意した方向性**:

- 授業計画に「数と式・計算を2コマ、図形を3コマ」のような、学習内容と予定コマ数の内訳を持たせたい。コメントだけでは、毎回の授業との対応やペースを扱いにくい。
- **内訳は必須にしない**。通常の案内は内訳なしで作成・送信でき、授業の記録も続けられる。毎回すべての授業に詳細計画を立てる負担を増やさない。
- 案内作成時には「高度な設定」などの任意の入口に置き、夏期講習等で必要なときに使う。具体的な見出し・操作は未確定。
- 内訳なしで案内した後に、講師が指導・ペース管理のために内訳を追加できる方向とする。
- **内訳を作ることと保護者へ公開することは別**。講師専用で使う場合と、保護者に位置付けを伝えるために公開する場合を区別する。後から作った内訳を自動公開しない。
- 学習内容の内訳と、既存の回数・料金の案内／承認／請求は別の役割。内訳の作成・修正だけを理由に、承認済みの総回数や料金を変更しない。

**承認回数が減った場合**: 10→8コマ等では、先生が手動で再配分する。公開版が超過した場合は調整中とし、合計が現在の回数以下になってから再公開する初回仕様を採用した。下書きは保持し、自動比例縮小・削除はしない。部分配分と内訳未設定を認める。

### 内訳内の「何コマ目か」を表示する

- **先生の追加要望**: 「予定2コマ」だけでなく、今回が `1 / 2` なのか `2 / 2` なのかも分かること。単元ごとのペース配分を把握できるようにする。
- **試作に反映した表示**: `方程式の計算` の近くに `今回 1 / 2 コマ目`、補足に `予定2コマのうち1コマ目`。先生の入力画面と、内訳を公開する場合の保護者向け表示の両方に示す。
- 分母は**対応する内訳の予定コマ数**、分子は**その内訳の中で今回が何コマ目に当たるか**。講習全体の `全10回`、計画全体の何回目、実施済み総数とは混同しない。
- `2 / 2` は「その内容が身に付いた」「単元が完了した」という評価ではない。理解度・学習上の到達は授業コメント等で伝える。
- 手入力欄は増やさず、授業との関連付けから自動表示する方向。算出対象・並び順・過去の訂正時の扱いは未確定であり、単純に保存回数を足す実装にはしない。
- 内訳なし・今回の内訳未選択・何コマ目か未設定を区別し、根拠のない回数を埋めない。`3 / 2` のような予定超過は隠さず示す案とするが、それだけで追加承認・料金請求・学習上の追加必要性を確定しない。
- 計画内訳の表示名と、実際に「扱った範囲」の入力は別。内訳を選び直しただけで、入力した教材・ページ・コメントを上書きしない。

### UX-01: ホームで優先すべき行動が下に埋もれる

**現状**: 先生ホームは全体の予定表と予定の編集が先にあり、今日の授業・取消依頼・未入金などが後に続く。生徒ホームは予定表、予定の編集、やることリスト、授業登録、授業計画の順。やることリストは初期状態で開いているが、授業登録と授業計画は対応待ちがあっても閉じている。

**影響**: ページを開いても今すべきことが分かりにくい。スマホ幅の再現では、宿題見出しがページ上端から約1,000px、返事が必要な授業登録が約1,300pxの位置にあり、最初の画面では見えなかった。

**改善案**:

- ホーム上部に役割別の要点を置く。先生は今日の授業と要対応、生徒は次の授業と宿題・返事、保護者は承認・確認が必要なものを優先する。
- 要対応の件数と対象への入口は、折り畳みを開かなくても分かるようにする。
- カレンダーは全体の把握・日付選択に使う。上部の要点と同じ授業一覧を何度も繰り返さない。
- 対応済み・空の項目は小さくまとめ、要対応があるときだけ強く示す。

**確認条件**: 主要な端末幅で、今すべきことと開始ボタンが最初の画面から分かる。対応待ちを見つけるためにすべての折り畳みを開く必要がない。

**根拠**: [管理画面](../kanri/index.html) の `renderHome`、[ポータル](../assets/portal.js) の `renderHomePage`、`folds`、`renderOffers`、`renderMonthSummary`。

### UX-02: 授業後の処理が分かれ、完了条件が分かりにくい

**現状**: 実施登録、授業記録の保存・公開、宿題の「やること」への反映は別処理。宿題は記録を保存した後に「反映する内容を確認」→「宿題を生徒へ反映する」と進む。記録への掲載と、チェックできる課題への反映は別の状態になる。

**影響**: 先生が記録に宿題を書いて保存しても、課題への反映を忘れる可能性がある。「この授業の後処理は全部終わったか」を複数の場所で確かめる必要がある。

**改善案**:

- 一つの授業画面で「実施」「記録公開」「宿題反映」の状況と残作業を示す。
- 授業後の処理を一続きに進められる導線にする。候補は、記録保存後に次の必要操作をその場で示す方式、または確認内容をまとめた完了操作。
- 内部処理を一括化するかどうかは別途設計する。途中失敗時は完了した部分と未完了の部分を分けて示す。
- 完了済み宿題の保護、二重登録防止、訂正履歴、先生メモの非公開性を継承する。

**確認条件**: 一つの画面で後処理の完了を判断できる。再試行で宿題が重複せず、既に完了した宿題の状態が失われない。

**根拠**: [管理画面](../kanri/index.html) の `lessonHTML`、`renderLessonHomework`、[授業記録処理](../gas/LessonCycle.gs) の `lessonRecordSave` / `lessonHomeworkApply` 分岐。分離の理由は [既存の授業サイクル仕様](LESSON_CYCLE_PHASE1_SPEC.md) を参照。

### UX-03: 前回情報・準備と、今回の入力欄が離れている

**現状**: 当日以降の授業記録画面では、今回の入力、宿題反映、保護者への報告下書きの後に、前回の記録・未完了宿題・授業準備が続く。

**影響**: 「前回を確認→今日の内容を判断→今回を記録」という作業で上下の往復が起きやすい。再現画面では、PC幅でも前回確認はページ上端から約2,200pxの位置だった。

**改善案**:

- PCは前回の記録・宿題・準備の要点を入力欄の隣に置く。
- スマホは入力欄の直前に参照用の短い要点を置き、詳細を必要に応じて開く。
- 通常の授業後処理で使わない報告下書きや履歴操作は、主な入力を妨げない位置にまとめる。
- 授業日・生徒・科目と保存状態が、長い入力中でも分かるようにする。

**確認条件**: 前回の宿題・準備を参照しながら入力でき、大きな上下移動を繰り返さない。二人同時の授業記録でも対象を取り違えない。

**根拠**: [管理画面](../kanri/index.html) の `lessonHTML`、`renderPreparation`、`renderLessonPair`。

### UX-04: メニュー分類から機能の場所を予測しにくい

**現状**: 生徒の先生への連絡・成績票と振り返りは「設定」にある。保護者の請求・計画承認・連絡・通知設定は「保護者メニュー」にまとまる。先生の「月間計画・請求」では、計画作成・承認状況・消化状況の後に請求が置かれる。

**影響**: 「質問したい」「成績票を見たい」「入金を記録したい」という目的から入口を選びにくい。大きな分類の中で再び探す負担がある。

**改善案**:

- 予定、学習・授業記録、連絡、料金、設定という利用目的で整理する。
- タブを一律に増やすことは前提にしない。役割と利用頻度に合わせ、主ナビと画面内の入口を分ける。
- 先生の計画管理と請求処理には、それぞれ直接到着できる入口を設ける。
- 生徒・保護者の共通の予定表と代行操作は維持し、保護者向けの承認・料金への入口を分かりやすくする。

**確認条件**: メニュー名から連絡・成績票・請求の場所を予測できる。設定には主にアカウントや通知の設定が集まる。

**根拠**: [ポータル](../assets/portal.js) の `renderTabs`、`parentNavigation`、`renderFamily`、`render`、[管理画面](../kanri/index.html) の `renderStudent`、`renderPlanCard`、`renderBilling`。

### UX-05: 通知・ボタンから目的の対象へ直接到着しない

**現状**: 先生ホームの「請求・入金を確認」は `#s=生徒ID` を開くため、初期の「予定」タブへ移る。生徒のお知らせの授業記録リンクは `#history` を開き、対象の記録ではなく科目・種類別のフォルダ一覧から探し直す。

**影響**: ボタンに書かれた用事をそのまま開始できず、クリック後も探し直しが発生する。

**改善案**:

- リンクに生徒・対象月・授業・記録などの文脈を引き継ぐ。
- 通知から対象の記録や承認欄を開き、該当箇所が分かるようにする。
- 戻る操作でも直前の一覧条件や日付を保持する。
- 対象が更新・削除された場合は、理由と適切な一覧への入口を表示する。

**確認条件**: 「請求・入金を確認」で対象生徒の請求欄へ、授業記録の通知で対象記録へ進める。移動先でも閲覧権限を確認する。

**根拠**: [管理画面](../kanri/index.html) の `renderHome` 内の未入金リンクと `route`、[ポータル](../assets/portal.js) の `studentNoticeItems`、`renderHistoryPage`、`hashchange`。

### UX-06: 似た用語が異なる手続きに使われている

**現状**: 「案内」「承認」「確定」が授業日時への返事と、回数・料金を含む計画の承認で使われる。「授業登録」という見出しの主な内容は、先生から届いた日時への返事。

**影響**: 誰が何を承認するのか、日程の確定と計画承認がどう違うのか、操作前に判断する必要がある。

**改善案**:

- 表示名は「授業日時への返事」「回数・料金の確認」など、対象と行為が分かる短い言葉にする。
- 状態は「生徒の返事待ち」「保護者の確認待ち」のように次の担当者を示す。
- 本人が今操作できるものと、相手の返事を待つものを区別する。
- 見出し・ボタン・通知・完了メッセージの用語を揃える。

**確認条件**: 日時への返事と計画の承認を、説明文を読み比べなくても区別できる。短い「登録不可」など既に整理した表現を、必要なく長くしない。

**根拠**: [ポータル](../assets/portal.js) の `renderOffers`、`renderMonthSummary`、[管理画面](../kanri/index.html) の `renderPlanGroup`、`offerForm`。

### UX-07: カレンダーの情報量と表示幅が合っていない

**現状**: スマホ幅では月間カレンダー内の授業文字が9pxになる。先生の週間予定表は最小幅930pxだが、通常のページ枠は最大860px。PC幅の再現でも予定表の表示領域は約811pxで横スクロールが生じた。週表示は初期状態で7時から始まり、予定表内とページ全体で縦スクロールが分かれる。

**影響**: 読み取りにくく、夕方の授業や週末へ到達するまでの移動が増える。スマホでは日付選択と詳細の読み取りを一つの小さな枠で行う負担が大きい。

**改善案**:

- スマホでは日別の予定一覧を中心にし、月表示を全体把握・日付選択に使う。
- PCの週表示には十分な横幅を与え、実際によく使う時間帯を最初に表示する。時間外の予定へも到達できるようにする。
- 色に加えて短い状態名を示し、詳細では時刻・科目・対象者を読みやすく表示する。
- 小さい文字やボタンの密集を避け、スマホでのタップとPCでのキーボード操作を確認する。

**確認条件**: 月表示から選んだ日の詳細を無理なく読める。通常のPC幅で週全体を把握でき、初期位置から主な授業へ進みやすい。

**根拠**: [月表示CSS](../assets/calendar.css)、[週表示CSS](../assets/schedule-board.css)、[週表示描画](../assets/schedule-board.js)、[管理画面](../kanri/index.html) の `.wrap`。

### UX-08: 保存・公開・反映の意味と、入力内容の見え方が揃っていない

**現状**: 授業記録は保存時に公開、報告下書きと準備は保存しても非公開、宿題は記録への掲載と課題への反映が別。保存ボタン近くでは「取り組み・次回の焦点」を公開すると説明しているが、現在の生徒・保護者の記録本文には当該項目を表示していない。

**影響**: 書いた内容が誰に見えるのか、どの操作まで行えば相手に届くのか、確信を持ちにくい。

**改善案**:

- 入力欄を公開する内容と先生専用の内容に整理し、公開先を近くに示す。
- 保存後に「記録は公開済み・宿題は未反映」など、結果と残作業を具体的に表示する。
- 実際の公開画面と保存前の説明を一致させる。
- 「取り組み」「次回の焦点」は、公開画面に出すか先生用に整理するかを検討する。既存の入力項目の削除保留の判断は維持する。
- 標準期限が既に設定されている宿題で「＋期限を設定」とだけ示す箇所は、現在の期限と変更操作が分かる表現を検討する。

**確認条件**: 各項目の公開先、保存結果、宿題の反映状態を画面から判断できる。先生だけのメモや準備が生徒・保護者へ公開されない。

**根拠**: [管理画面](../kanri/index.html) の `lessonFields`、`lessonHTML`、[ポータル](../assets/portal.js) の `publishedRecordItem`。[既存の未決事項](FUTURE_WORK.md) の「授業記録の入力項目の整理」と併せて扱う。

### UX-09: エラーと再試行の示し方が機能によって異なる

**現状**: 授業記録等には入力保持・未完了表示・再試行がある一方、予定や宿題の一部の入力エラーは約2.8秒で消える画面下の通知で示す。

**影響**: 通知を見逃すと、どの入力を直すべきか、保存されたか、もう一度押してよいかが分かりにくい。

**改善案**:

- 入力エラーは該当欄の近くに残し、必要ならその欄へフォーカスを移す。
- 通信・保存失敗は操作箇所の近くに、入力保持の有無と再試行方法を示す。
- 保存中・完了・未完了の表現を揃える。短時間の通知は補助として使う。
- 保存結果が不明な場合は、既存の処理IDによる再試行など、重複を防ぐ方式を継承する。

**確認条件**: エラー表示を見逃しても修正箇所と未完了の作業を再確認できる。入力を失わず、二重送信が起きない。

**根拠**: [ポータル](../assets/portal.js) と [管理画面](../kanri/index.html) の `toast`、入力検証・保存処理、既存の授業記録・請求の再試行UI。

## 4. 配置と導線の方向性（候補）

| 利用者 | ホーム上部で分かること | 主な作業の流れ |
|---|---|---|
| 先生 | 今日の授業、返信・取消等の要対応、記録漏れ | 今日の授業 → 前回・準備を確認 → 記録 → 宿題反映・完了確認 |
| 生徒 | 次の授業、期限の近い宿題、日時への返事 | 宿題を確認・完了／案内に返事／予定表から授業可能日時を登録 |
| 保護者 | 確認・承認が必要な内容、子どもの直近の授業・記録 | 対象の計画・請求・記録を直接開く → 確認・承認・連絡 |

この表は主ナビの最終案ではない。生徒・保護者の共通カレンダーを維持しつつ、役割ごとの要点と専用操作の入口を調整する。兄弟まとめ予定表は既存の別課題として扱い、今回の整理から自動的に追加しない。

## 5. 改善の優先順位

**現在の優先順位**: 先生の指定により、授業記録を最優先とする。対象はUX-02・03・08・09と、上記の授業計画との対応。初回改修・保護者ログインの修正と本番家族経路の確認は完了。次はmirror確認と実運用での入力負担を評価する。その他の課題の着手順は未確定。

以下は初回調査での推奨順を判断の経緯として残したもの。ホーム優先を現在の合意として扱わない。

| 順番 | 対象 | 最初に具体化すること | 効果の確認 |
|---|---|---|---|
| 1 | UX-01・05 | ホームの優先順位、請求・通知から対象への直接移動 | 対応待ちを発見し、対象画面を開くまでの迷い・操作数 |
| 2 | UX-02・03 | 授業中の参照と入力、授業後の完了までの流れ | 記録と宿題反映に要する往復、反映忘れ、完了判断 |
| 3 | UX-04・06 | 機能の分類、ナビ・見出し・状態名 | 初見で連絡・成績票・請求の場所を見つけられるか |
| 4 | UX-07 | PCの週表示とスマホの日別表示 | 小さな文字、横・縦スクロール、対象日の選びやすさ |
| 5 | UX-08・09 | 公開先、保存状態、エラー・再試行の共通表現 | 誰に何が反映されたか、失敗後に何をすべきか分かるか |

順位は初回評価での推奨。UX-08・09の説明不一致や消えるエラーなど、小さく直せるものは各画面の改善と同時に扱える。開発工数と実業務での効果は未見積もり。

## 6. 維持する長所と既存の判断

- 単元とコメントを中心にした記録入力、次回の同じ科目を使う宿題期限、一括確定、先生からの表示専用プレビューは活かす。
- ホームの同じ予定の重複表示を増やさない。要点と詳細にはそれぞれ役割を持たせる。
- 授業可能日時は開始・終了時刻と任意メモで直接登録できる流れを維持する。
- 記録保存・宿題反映を分離した既存の理由を確認してから操作を統合する。画面上の一連化と、データ処理の一括化を同一視しない。
- 保護者の既読、計画への承認、授業日時の確定、請求・入金は、それぞれの意味を保持する。
- UI変更だけを理由にデータ項目の削除、公開範囲の拡大、請求条件・取消規則の変更を行わない。

## 先生からの指摘：カード主体の画面が使いづらい（2026-10-01）
